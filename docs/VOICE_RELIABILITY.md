# 语音可靠性与延迟修复

目标：保留现有录音、通话、本地引擎和文字练习，减少结束说话后的等待；失败时保留整句录音，不把半句作为最终回答。

2026-10-27 的实测显示，同样合成音频在本地连接讯飞时识别约 2–3 秒，经过生产 Render 后端时约 8–15 秒。前一轮仅调整连接与超时的修复不足以解决生产链路延迟。

## 实施选择

- 继续使用当前海外中转：部署简单，保留为兜底；无法消除额外的音频传输路径。
- 浏览器直接连接讯飞，后端签发短期连接授权：作为本次实现选择；不使用浏览器内置识别，API Secret 只留在服务端，授权不写入持久存储或日志。
- 迁移后端区域：需要额外云端资源和部署决策，不在本次修复中直接执行。

直连只改变传输路径，维持现有 16 kHz 单声道 PCM、英文识别和 UI。浏览器连接失败时继续使用既有后端；一段时间内跳过重复失败的直连尝试。讯飞业务错误不无限重试，用户取消操作立即释放连接。

## 实施与验收顺序

1. 先用失败用例覆盖短期授权的缓存与密钥边界、直连帧序列、完整转写、取消与失败兜底。
2. 实现后端短期授权接口、共享的浏览器直连客户端，接入录音和实时通话，保留原中转路径。
3. 完整运行前后端测试、代码检查和构建，独立审查后推送 main。
4. 确认前后端部署引用同一代码提交，再进行生产实时/录音识别和隔离浏览器点击验收。
5. 自动注入的合成录音标记为数字音频测试。物理麦克风收音和实际朗读另行验收。

前一轮已经补齐：有限连接重试、连接关闭等待限制、完整录音兜底、超时/错误连接退役、短音频结束标记与空结束帧文本保护。最终生产结论与保留测试数据记录见 `design-qa.md`。

## Windows 真机复测

2026-11-10 在正式站点咖啡馆场景使用 Windows 的物理麦克风阵列与 Realtek 扬声器。系统音量维持 5%，扬声器播放合成测试句，中间插入 800 ms 静音。两种浏览器都获得了真实麦克风的 48 kHz 轨道，并启用浏览器降噪、回声消除和自动增益。测试拦截了识别连接与录音上传，麦克风音频留在本机。

| 浏览器 | 物理麦克风结果 | 文字请求至系统回录首声 |
|---|---|---:|
| Chrome 156.0.8078.75 | 两次尝试均触发语音识别，第二次的输入峰值 RMS 约 0.020，触发了一次被测试拦截的录音上传 | 1.09 秒 |
| Edge 157.0.4341.42 | 捕获到输入，并尝试建立识别连接。观测窗口内未看到整段录音上传 | 1.68 秒 |

首声分别是 Chrome `qa-device-chrome-mwauy0rb` 和 Edge `qa-device-edge-mwauyfut` 的单次文字对话样本。两次均用本地 Microsoft Mark 朗读。WASAPI 系统回录按实际音频回调计时，从进入朗读队列后寻找持续声段，排除发送按钮的提示音。Chrome 在发送前模拟浏览器离线，显示「重试回复」，恢复联网后点重试收到回复并正常朗读。

一次追加的 Chrome 尝试在允许发送的测试句窗口内没有触发录音上传，窗口内观测的峰值 RMS 约 0.007。这说明在本机 5% 扬声器音量下，物理回录并非每次都能达到自动判停门槛。用页面的手动录音按钮重测时，生产识别接口收到一次上传并返回 HTTP 200，但没有返回文字（`qa-device-chrome-mwav1ixl`）。这次没有发送聊天回合，也没有达到完整转写验收。

## iPhone Safari 真机验收

2026-11-11（北京时间），使用 iPhone 原生 Safari 在正式站的咖啡馆场景测试。电脑播放固定 WAV，iPhone 物理麦克风收音。转写、消息次数、实际出声和麦克风指示均由测试者在手机上确认。

| 用例 | 结果 |
|---|---|
| 首页与练习入口 | 首页排版和导航正常，可进入咖啡馆。 |
| 实时通话短答 | “Yes, please.” 正确转写，页面显示一条用户消息，实际听到 Pip 回复。挂断后麦克风指示消失。 |
| 800 ms 句中停顿 | 3/3 通过。点单内容和尾句 “Can I pay by card?” 保留在同一条消息里，每轮只显示一条用户消息。 |
| 手动录音 | 停止录音后页面显示一条正确的短答，实际听到回复，麦克风指示消失。 |

机型、iOS 版本和后台 Trace 未采集。通话中实际断网恢复按要求跳过。
